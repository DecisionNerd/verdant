# Annotation and truth management

Verdant consumes the external OSS Label Studio image. It owns assignment,
provenance, agreement, review and truth records; it does not implement a second
authentication bridge, editor, project ACL or experiment engine.

The implemented task is **single categorical text**. A task schema includes an
ordered category set, instruction text and instruction revision. Its native XML
is generated by `CategoricalSchema.native_xml()`. Other labeling modalities fail
explicitly. This slice supports at most 500 dataset members, 100 native tasks in
a project (1 MiB export), 10 assigned contributors per task/report, 100 report
units, 100 cohort contributors, and 1,000 original revisions per assignment.
A categorical native result is at most 64 KiB; native HTTP responses are capped
at 1 MiB before decoding. Listing APIs have bounded cursors.

## Operator admission and deployment

Set `VERDANT_LS_BROWSER_ORIGIN`, `VERDANT_LS_MACHINE_ORIGIN`,
`VERDANT_LS_IMAGE` (digest-pinned), and the private `VERDANT_LS_TOKEN`.
Origins must be distinct canonical HTTPS origins. `VERDANT_LS_CA_BUNDLE` optionally
selects a verified private CA bundle; TLS verification remains enabled.
The native service account must be explicitly registered in the external image,
remain unbound to a human and be reachable only through the private machine
origin. Credentials never enter the browser or a registry snapshot.

Each Community instance is one shared-trust cohort. Projects do not isolate
contributors or provide blind annotation. Separate trust cohorts require separate
instances, data, credentials and media access. A cohort origin can be admitted to
only one Verdant namespace. Namespace access is checked before rows/counts and
again at serialized command boundaries. Current contributor namespace admission
is checked before imports. Native Keycloak admission/offboarding must also be
operated externally; removing a Verdant grant does not erase data already visible
to an externally admitted shared-trust user.

Use the trusted operator CLI, never a workspace HTTP endpoint:

```sh
uv run python -m verdant.annotation_operator admit-cohort NAMESPACE_UUID \
  --name 'Team shared trust' --issuer https://identity.example/realms/team \
  --reason CHANGE-REFERENCE
uv run python -m verdant.annotation_operator bind-contributor COHORT_UUID \
  --issuer https://identity.example/realms/team --subject VERIFIED-SUBJECT \
  --native-user-id 42 --reason VERIFIED-INVENTORY-REFERENCE
```

Provision exact Verdant identities/grants first. Verify `(issuer, subject)` and
native ID through external identity administration and the native operator
inventory. Email is never a join key. The binding is immutable. `--reviewer`
explicitly admits canonical-review authority; ordinary namespace writers cannot
self-grant it. Repeating the exact admission is idempotent. New native bindings
cannot reuse an admitted native ID or principal. Revoke a human through identity
admission/grants and the external native operator rather than reassigning history.

An operator prepares the native project with the exact generated categorical XML
and disables both `evaluate_predictions_automatically` and
`show_collab_predictions`. Native task data must contain exactly `text` and
`verdant_revision_id`. The UTF-8 text digest must equal the selected immutable
source revision. This prevents answer-bearing native task metadata from becoming
an assignment source. No human credential or fork edit is required.

## Workspace path

Open a dataset, choose an admitted cohort and independent contributors, select
an exact current member, enter its prepared native project/task IDs, and create
an assignment. Verdant verifies schema/instructions, project membership, text
content and revision, then stores immutable pins. Open the allowed native stock
editor origin, use your own SSO session, and return to the workspace tab. Import
fetches authoritative native records; URL parameters/callback content never
supply annotation or contributor identity. An unavailable or mismatched instance
fails closed and retains input/evidence.

The adapter verifies native task data through bounded project export. It fetches
annotations only through `/api/tasks/{id}/annotations/`; it never calls native
`TaskAPI.get`, which can evaluate predictions. HTTP requests forbid redirects,
request identity encoding, reject compression before raw streaming, and enforce
a byte cap before JSON decoding. The browser's stock UI retains its native
behavior; automatic project prediction features must remain disabled.

Strict positive integer native author/modifier IDs (including expanded objects)
resolve through admitted mappings. Changes create immutable original revisions;
cancellation/deletion appends history. A content reversion creates a new revision
even if its digest matches an older original. Duplicate imports commit no extra
effects. Stale counts, changed schemas/tasks/authors, unknown contributors and
ambiguous multiple active originals fail atomically.

Native `updated_by` is retained. Cross-author modifications preserve the original
native author and mapped modifier, and make effective independence unknown.
Missing modifier provenance also cannot count as independently authored overlap.
Assistance is self-declared; shared-trust visibility means blindness is unverified.

Agreement reports pin exact original IDs/digests and task/instruction/schema
identity. They expose pairwise overlap, missing/abstention/assistance counts,
confusion counts, marginal prevalence, observed agreement with 95% Wilson bounds,
and Cohen kappa. Empty overlap and constant identical marginals return explicit
undefined values. Wilson bounds assume independent task pairs; correlated groups
need grouped inference. Kappa uncertainty is not estimated. Agreement is not
correctness. A side-by-side queue identifies disagreement and incomplete cases.

An admitted reviewer records rationale and creates a new canonical annotation and
review pin. An unresolved review is retained but excluded from labeled truth.
Stale reports or canonical heads are rejected. Corrections append a prior-linked
identity. Original evidence and pre-adjudication reports never change. Chain-leaf
head selection avoids PostgreSQL transaction-start timestamp ordering races.

## Truth partitions and audits

Truth publication assigns every current exact dataset member atomically to typed
train, validation, test or production partitions. Train/validation/test require
exact reviewed canonical annotation/schema/review pins. Existing transformation
pins are retained. Production remains unlabeled unless explicit reviewed audit
selection is recorded. The snapshot and membership revision remain immutable and
can be captured/published with existing registry/versioning services.

Absent validation is derived from train before tuning: connect declared source
groups and identical content, sort components by SHA-256, and take the first 20%
(round down, at least one). At least two separable components are required.
Group IDs and content digests cannot cross current partitions. Missing group IDs
fall back to sample identity; undisclosed real-world grouping cannot be detected.

Preserving an unchanged test partition while publishing a production audit is
not evaluated test reuse. Moving historical test groups/content into train or
validation requires an explicit exploratory-contamination disclosure. A separate
`evaluation_use_declaration` can record a caller's exploratory-test-use declaration;
this service does not observe or certify experiment usage. Fresh confirmation
requires test groups/content absent from prior truth snapshots and an exact
prior truth ID/digest. It cannot certify that labels were never seen elsewhere.

Production audits pin the original production truth ID/digest, source revision,
selection stratum, inclusion probability, selection method, canonical truth and
reviewer. Audited samples remain production and cannot silently become holdouts.
These declared selection facts do not create an unbiased population-quality
estimate. Old manifests or experiment-like references retain exact old truth,
canonical, schema, review and membership identities.

Evaluated model input is owned by epic 4's `model_inputs.project_model_input`:
verified artifact bytes only, strict UTF-8 text and 64 KiB. Interpretation, truth,
review, group/audit and all source metadata are excluded from that function's
signature. This slice does not implement an experiment engine.

## Migration and proof

`0022_annotation` is additive over `0021_availability`. It creates immutable
cohort/contributor/assignment/original/report/canonical/truth tables. PostgreSQL
triggers reject update/delete. Prior migrations are untouched. Upgrade with the
normal release migration process; retain data when rolling application code back.
The epic 4 sibling has a separate `0022_process` head; integration owns the merge
migration and combined schema-readiness revision.

Focused proof: `tests/test_annotations.py`, `tests/test_label_studio.py`, workspace
component tests, and `apps/workspace/e2e/truth.spec.ts`. The browser fixture owns
only project `verdant-truth-bc0aaa6b` and ports 192xx, a fresh PostgreSQL `_test`
database, S3, HTTPS Keycloak, and the installed qualified native image. Generated
secrets/CA/session material stay ignored under `e2e/truth/.local`; traces are off.
The existing lifecycle spec is unchanged. See `docs/proofs/epic-5/` for the actual
run receipt and any unresolved acceptance limits.
